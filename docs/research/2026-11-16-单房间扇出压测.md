# 单房间扇出压测：Room 广播的实际数字

- 日期：2026-11-16
- 工具：`cmd/roomload`（新建）
- 环境：Windows 开发机，单进程 imchat，SQLite 单写者，WAL
- 目的：回答 #25「单房间 1 万在线」是否成立

## 方法

1. 登录一个账号，在默认社群开一间新房；
2. 分批（每批 100）建立 N 条 WebSocket 连接，全部挂在该账号下（多端）；
3. 每条连接读循环记录 `msg` 帧的到达时刻，按 `seq` 归档；
4. 发送 M 条房间消息，记录发出时刻；
5. 计算每条消息到每条连接的延迟，取分位。

房间消息走广播、不进待投递队列，所以这个数字只反映扇出路径，
不包含 outbox 的重投成本。

## 数据

| 连接数 | 建连耗时 | 消息数 | 投递数 | 期望 | 丢失 | p50 | p95 | p99 |
|---|---|---|---|---|---|---|---|---|
| 1000 | 1.16s | 5 | 5000 | 5000 | 0 | 3ms | 5ms | 6ms |
| 3000 | 3.56s | 3 | 9000 | 9000 | 0 | 10ms | 17ms | 19ms |
| 5000 | 5.97s | 3 | 15000 | 15000 | 0 | 16ms | 28ms | 29ms |

## 结论

1. **单机 5000 条长连接、单房间广播零丢失，p99 < 30ms。**
   延迟随连接数近似线性增长（1000→5000 时 p99 从 6ms 到 29ms）。
2. **1 万连接未在本机验证**：Windows 上 10000 条 WS 连接会撞到端口与句柄上限，
   这不是服务端的问题，是压测机的问题。按线性外推，1 万时 p99 约 60ms，
   但必须以 Linux 压测机复核后才能写进容量承诺。
3. **消息扇出不是瓶颈。** 5000 连接 × 3 条消息只用了不到 6 秒建连时间之外的开销；
   真正的成本在媒体侧（1 万订阅者的音频出向约 320 Mbps），见
   [万人聊天室的容量与媒体边界](./2026-11-16-万人聊天室的容量与媒体边界.md)。

## 未回答的问题

- 1 万连接的 Linux 复核（需要一台更大的压测机）。
- 50 个并发发言者同时写时的序号竞争（当前压测只有 1 个发送者）。
- 连接建立/断开的抖动对广播的影响。

## 复现

```bash
go build -o bin/imchat.exe ./cmd/imchat
go build -o bin/roomload.exe ./cmd/roomload
./bin/imchat.exe -addr 127.0.0.1:18095 -db ./data/load.db -seed -open=false &
./bin/roomload.exe -base http://127.0.0.1:18095 -subs 5000 -rounds 3
```
