# ADR-0001 单机单文件：SQLite + Go 单二进制

- 状态：已接受
- 日期：2026-11-14

## 背景

本项目的第一交付约束不是吞吐，而是**评审者能不能在自己机器上零依赖跑起来**：一个可执行文件、
一个数据文件、打开浏览器就能看到两个人真的在聊天。

最初选型倾向 PostgreSQL + Redis，理由是关系约束强、能讲横向扩展。但这两个东西都需要额外
安装或容器编排，把"跑起来"从"双击"抬成"装 Docker、等镜像、看日志排错"。而真正会把自己机器
跑起来看的评审者不到十分之一。

## 决策

1. 存储：SQLite（WAL 模式），单文件，位于 `./data/imchat.db`。
2. 驱动：`modernc.org/sqlite`（纯 Go，CGO 关闭），保证 `GOOS/GOARCH` 交叉编译产出单文件。
3. 交付：前端构建产物通过 `go:embed` 编进二进制；最终产物 = 一个可执行文件 + 一个数据目录。
4. 扇出：进程内内存 Hub（`map[userID] → 连接集合`），不使用 Redis Pub/Sub。
5. 队列：不引入消息队列。持久化投递用 SQLite 中的 outbox 表 + 单写者 goroutine。

## 后果

正面：
- 零依赖启动：运行二进制 → 浏览器打开 `http://localhost:8080`，无外部服务。
- 数据即文件：可拷走、可用任意 SQLite 工具审阅，"数据在哪"没有黑箱。
- 写路径天然串行：单写者 + WAL 使"取号 + 落库"处于同一事务，会话序号不会出现空洞。

负面：
- 写并发受单写者限制。本项目的量级远未触顶，但这是真实天花板，不能假装不存在。
- 无法用"多实例 + 共享存储"证明横向扩展；扩展只能作为设计论述，不能作为运行事实。
- "PG 分区表承载海量消息"的叙事不再成立，改为"单机内的正确性"叙事。

## 备选方案

- PostgreSQL + Redis：一致性表达最干净，但违反零依赖约束，且要额外讲部署。
- SQLite + `mattn/go-sqlite3`：性能略好，但依赖 CGO 与平台工具链，交叉编译单文件失败。
- 纯内存存储：重启即丢，与"可靠性工程"主线直接矛盾。

## 必须讲清楚的边界

SQLite 的并发写入是单写者。这不是缺陷，而是本项目的**明确设计点**：所有写事务进入同一个
writer goroutine，用串行化换取"取号与落库的原子性"，于是"消息序号连续"成为可证明的性质，
而不是概率性的事实。这个取舍本身，就是面试里值得讲三分钟的题目。
