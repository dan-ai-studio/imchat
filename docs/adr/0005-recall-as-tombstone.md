# ADR-0005 撤回是追加，不是修改

- 状态：已接受
- 日期：2026-11-14

## 背景

GLOSSARY 里写着"消息一旦产生即不可变"。现在要加撤回功能，这句话立刻被顶到墙角：
用户撤回了，那条消息算不算被改了？

两种实现都能"看起来能用"：

1. 原地修改：给消息行加 `recalled_at`，撤回时 UPDATE。
2. 追加墓碑：新写一条 `kind=recall` 的消息，用 `recall_of` 指向被撤回的 seq。

## 决策

采用**追加墓碑**。

理由不是洁癖，而是三条具体的后果：

- **序号连续性**：撤回占一个新的 seq，客户端的缺口检测不需要知道"有些 seq 会消失"。
  如果原地改，这条消息在同步里是"仍在但已失效"，每个客户端都要多写一条分支。
- **可追溯**：谁在什么时候撤回了什么，本身就是一条消息，参与同一套补投与去重。
  原地改会把这段历史变成一次静默的 UPDATE，审计上等于没有。
- **幂等与乱序**：墓碑和普通消息走同一条 outbox 路径。如果撤回是原地改，
  它就要额外设计一条"状态变更"的投递通道，重复与乱序问题要重新解一遍。

## 后果

正面：
- 消息表保持只追加（append-only），"不可变"这句话仍然成立。
- 撤回沿用既有的序列号、待投递记录、ack、补齐：零新增投递机制。
- 历史查询一次就能拿到"消息 + 它的撤回标记"。

负面：
- 每条撤回占用一个会话序号。
- 客户端渲染时要多做一步：见到 recall 帧，回头把目标 seq 标成已撤回。
- 如果客户端从中间开始拉历史，必须把 recall 消息也拉下来，否则会漏掉失效标记。
  本项目的历史接口本来就返回全部消息（含 recall），所以这一条自动成立。

## 备选方案

- 原地 UPDATE `recalled_at`：实现最短，但破坏了只追加，且需要为"状态变更"另造一条投递路径。
- 物理删除：直接违反可靠性主线——删掉的东西没有任何机制能证明它被删对了。
