# ADR-0006 讲解写进源码，不另设并行文档

- 状态：已接受
- 日期：2026-11-15

## 背景

README 论证"为什么这么设计"，GLOSSARY 定义领域词汇，ADR 记录取舍，docs/DEPLOY.md 讲部署。
四者齐备，唯独缺一类东西：**这一行为什么这么写**——读者站在某一行前面时需要的解释。

实测：Go 3,200 行只有 95 行注释（约 3%），`internal/auth/auth.go`、`internal/store/models.go`、
`internal/store/session.go`、`internal/api/recall.go`、`internal/store/conversation.go`、
`cmd/loadtest/main.go` 等 9 个文件一条注释都没有；`internal/store/schema.sql` 76 行零注释。
源码是这个仓唯一没有讲解的地方，却又恰好是读者唯一必须停留的地方。

## 决策

讲解**写进源码本体**，不另建一份平行文档。

同一位置分两层，用位置而非前缀区分：

| 层 | 位置 | 语言 | 读者 | 进 godoc |
|---|---|---|---|---|
| 契约注释 | 声明上方 | 英文 | 维护者 | 是 |
| 讲解注释 | 函数体内 | 中文 | 会编程但不写 Go 的人 | 否 |

Go 的 doc 工具只取声明上方的注释，函数体内的注释不进任何文档输出。这条事实让两层永不抢同一块位置：
`go doc ./internal/store` 仍然输出给维护者的英文契约，中文讲解只出现在读代码的人眼前。

**中文讲解不翻译既有的 95 行英文契约。** 那段是全仓信息密度最高的部分（`appendInTx` 上方那段
就是"取号与落库同事务"论点的原文），翻译等于重写，并且会与 ADR 的措辞分家。

**可验收的形状**：每个 func / type 声明上方有契约注释；函数体内不得出现连续超过 8 行无讲解的代码
（`import` / `var` / `const` 块与 struct 字段除外）。这条规则可被脚本检查，"完整"因此是数得出来的。

**纯闭合行不算**：只有 `}`、`)`、`]` 的行，以及只有一个 HTML/Vue 闭合标签（如 `</div>`）的行，
都不携带逻辑。模板里连着四五个 `</div>` 与 Go 里连着几个 `}` 是同一类东西——把上面打开的那一层
收回去。段与段之间的收口不该被算成"没人讲"，否则注释就得写进标签之间的缝隙里，那反而是噪音。
这条边界由 `cmd/notescheck` 的 `closingOnly` 与 `htmlClose` 实现。

注意 `internal/store/db.go` 与 `web/embed.go` 各有一处 `//go:embed`：契约注释写在该指令之上，
指令必须紧贴其 `var`，中间不得插入任何内容。

## 后果

正面：
- 讲解与代码同一次提交、同一个 diff：不存在"行号漂移"这个失效模式。
- 读者不必离开文件就能读懂，跳转成本为零。
- 注释在 review 时立刻可见，撒谎的成本比藏在 docs/ 里高一档。

负面：
- 生产代码被写成给初学者看的样子。半年后的贡献者读到中文讲解会问"为什么产品代码这样写"
  ——这份 ADR 就是回答。
- 删除成本高：合并后是数千行中文注释，撤掉等于第二次大改。
- 两层注释语言不同，`go doc` 的输出与源码内的语言不一致，新人需要接受一次解释。
- 注释会随代码改动而失真，而静态工具检不出语义层面的撒谎，只能靠纪律与 review 兜底。

## 备选方案

- **独立文档**（`docs/` 下 Markdown + `file:line` 锚点）：最干净，但行号会漂移、讲解与代码双份维护，
  且读者读代码时仍要跳到另一个文件再跳回来。否决的主要理由是最后这条：讲解不在读者眼睛所在的地方。
- **带注解的源码副本**（如 `docs/annotated/message.go.md`）：排版更自由，但副本会被误认为真源码，
  且它是真源码的第二份——双份维护里最坏的一种。
- **交互站点**（左源码、右讲解）：教学体验最好，但等于再开一个项目，要构建、要托管、要跟 README 同步，
  与本项目"一个二进制、零外部依赖"的姿态相冲突。
