# ADR-0007 从可靠性演示转向可运营产品

- 状态：已接受
- 日期：2026-11-16

## 背景

README 的第一性论证是「当连接会断、进程会崩、同一个请求会到达两次，一套 IM 凭什么说自己没有丢消息」；
[ADR-0001](0001-sqlite-single-file-deployment.md) 据此把「评审者能在自己机器上零依赖跑起来」写成第一交付约束，
[ADR-0003](0003-embedded-broker.md) 据此把扇出实现为进程内 broker。

新需求（可运营、有等级、可视频、可语音、万人聊天室、可管理、产品级）要求的是另一套第一性约束：
真实用户、容量、运维面、内容风险。两个第一交付约束不能同时写进同一个仓库而不互相削弱。

## 决策

本仓转向可运营产品，三条：

1. **「零外部依赖」从第一交付约束降为默认开发形态**：开发仍是一键启动；生产允许多进程、多机。
2. **「至少一次投递 + 会话序号稠密」保留为差异化内核**：它是这个产品区别于通用 IM 的唯一论证，不随定位改变而放弃。
3. **ADR-0001 与 ADR-0003 不作废，改为「适用范围」限定**：它们描述默认开发形态与扇出边界，不再描述生产容量承诺。

## 后果

- 生产形态从「一个二进制」变为「应用进程 + 媒体进程」，万人订阅需要多媒体节点级联。
- 数据模型从全局单例变为多租户，`community_id` 成为所有查询的必带维度。
- 「单机单文件」不再能充当容量论证；容量论证必须来自压测。
- 权限主体从两套正交变为三套正交（新增 Community Admin）。

## 未采纳

- **分叉成两个仓库**：协议与存储内核要维护两份，而演示价值可以由 README 保留。
- **保持演示定位、把万人房间做成可演示模块**：那会让「产品级」变成无法验收的形容词。
