# ADR-0003 嵌入 broker 作为扇出总线

- 状态：已接受
- 日期：2026-11-14
- 实现选型：NATS core（进程内嵌入，不启用 JetStream）

## 背景

ADR-0001 定下"单机单文件、零外部服务"的交付形态，并把连接扇出实现为进程内 map 遍历。
项目负责人要求架构中存在一个**显式的消息总线边界**，而不是把扇出写成一次 map 遍历。

## 决策

1. 在 Go 进程内嵌入 `nats-server`，通过 `nats.InProcessServer()` 建立内存连接，不占用额外端口对外。
2. **不启用 JetStream**。JetStream 需要 StoreDir，会引入独立数据目录，破坏"单文件"约束。
3. broker 只承担**瞬时扇出**；持久化由 SQLite 的待投递记录承担。
4. 数据流：
   写事务提交（消息 + 待投递记录）→ 投递器发布到 broker →
   连接层订阅并下发 → 客户端 ack → 消解待投递记录。
5. 主题约定：`user.<user_id>` 送达；后续可加 `conv.<conversation_id>` 做会话级订阅。

## 后果

正面：
- 扇出成为可替换边界：进程内 broker 与独立集群之间只改连接配置（`nats.Connect(url)`）。
- 订阅生命周期与连接生命周期解耦，多端订阅表达自然。
- 架构图上是一个真在跑的组件，不是贴上去的 Kafka 图标。
- 重启安全性由 SQLite 保证：broker 是内存的，但未确认的待投递记录会在重启后重投。

负面：
- 二进制体积增加约 10~15MB。
- 单机场景下多一层序列化，是纯开销。
- 必须能回答"单进程为什么需要 broker"。本项目的答案：**broker 划出的是替换边界，不是吞吐边界。**

## 备选方案

- 进程内 map 扇出：零开销，但没有可替换的扇出边界。
- mochi-mqtt：也是进程内可嵌入。但 MQTT 的 QoS 0/1/2 会让人误以为 broker 保证了可靠投递，
  而内存 broker 重启即丢，等于埋下一个必须当场解释的坑。
- 独立 NATS / Redis 进程：破坏单文件约束，否决。
