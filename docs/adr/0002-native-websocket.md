# ADR-0002 实时通道：原生 WebSocket + 自定义帧协议

- 状态：已接受
- 日期：2026-11-14

## 背景

项目主线是可靠性工程，可展示的核心动作包括：断线重连后的缺口补齐、投递确认、多端已读同步、
在线态。这些动作恰好是"讲不讲得清楚"的分水岭。

## 决策

1. 服务端使用 `coder/websocket`（原 `nhooyr.io/websocket`），不引入 Socket.IO 服务端。
2. 应用层自定义 JSON 帧，共六类：`hello` / `send` / `ack` / `read` / `presence` / `ping`。
3. 前端使用浏览器原生 `WebSocket`，不引入 `socket.io-client`。
4. 连接层只负责收发帧与心跳，不承载业务语义；业务语义全部落在 service 层。

## 后果

正面：
- 重连与补偿是核心叙事，原生实现让每一行都能被追问到细节。
- 协议自成文档：六种帧可以画成一张状态机图。
- 前端零 SDK 依赖，行为完全可解释。

负面：
- 需要自己实现重连退避、心跳超时、半开连接检测、帧大小上限与读超时。
- 没有房间广播、没有自动 ack，全部手写。

## 备选方案

- Socket.IO：自动重连/房间/ack 全部内置，开发更快。但它把"可靠性"抽象成了黑盒，
  而这正是本项目要展示的对象，用黑盒实现等于把亮点外包。
- SSE + HTTP POST 上行：单向下行，做不了"输入中/在线态"这类双向小事件，且需要额外解释取舍。
- gRPC streaming：web 端需要 grpc-web 代理，与"单文件零依赖"冲突。
