# 阅读总图

这份图只回答一件事：**按什么顺序读**。

它不讲每个模块做什么（那是 `README.md` 的「目录」），也不讲为什么这么设计（那是 `docs/adr/`）。
三类信息各归其位，互不重复。

## 怎么用

从第 1 站开始，顺着读。每一站的文件里都有一块**导航块**（放在 `package` 子句之后），长这样：

```go
// ── 阅读导览 · 第 5 站 ──────────────────────────────────
// 上一站：站4 发送的前半
// 下一站：站6 投递器
```

导航块只说站号和前后站，不说这一站干什么——职责的唯一出处是这里的表格。所以你打开任何一个文件，
都知道自己站在路线的哪个位置、下一步去哪。

**不懂 Go 也能读**：声明上方的英文注释是写给维护者的契约（它承诺什么），函数体内的中文讲解是写给
你的（它怎么做到）。第一次出现 Go 的语法时，会当场解释一次。

## 主线：一条消息的一生

一条消息从"用户按下发送"到"被确认收到"，是这样走的：

| 站 | 这一站回答什么 | 落在哪里 |
|---|---|---|
| 1 | 这个进程由什么组成，优雅关闭为什么要把启动顺序反过来 | `cmd/imchat` |
| 2 | 一个 HTTP 请求怎么变成一条长连接，服务端凭什么相信它属于某个人 | `internal/api`、`internal/auth` |
| 3 | 线上跑的是什么：上行下行各有哪些帧，为什么只有确认帧能改状态 | `internal/ws` |
| 4 | 消息进入系统的唯一写路径：校验、@ 解析、图片分支 | `internal/api` |
| 5 | 取号与落库为什么必须在同一个事务里——序号不可能有空洞的来源 | `internal/store`（先读建表语句） |
| 6 | 已经落库的消息怎么被真的送出去：按到期扫描、重试与退避 | `internal/delivery` |
| 7 | 一条消息怎么变成"所有接收者的所有终端各一份"，以及 broker 为什么可以被换掉 | `internal/bus`、`internal/ws` |
| 8 | 抵达终端的最后一跳，确认回来之后待投递记录怎么消解 | `internal/ws` |
| 9 | 断线之后缺口怎么补，为什么只能补不能跳 | `internal/store` |
| 10 | 撤回为什么是再写一条消息，而不是改原来那条 | `internal/api`、`internal/store` |

读完这十站，你就走完了一条消息的一生，也摸到了这个仓的立身之本：**至少一次投递**。

## 主线之外

## 想动手改点什么

不用另找地图：站点本身就是入口。

- 想加一种消息类型 → 站 3（帧表）与站 4（写路径的分支）；
- 想换掉存储 → 站 5（取号与落库同事务）与站 9（补齐的读路径）；
- 想加一条群权限 → 旁路章的治理一节，那里并排讲了会话内角色与平台管理员；
- 改完记得同步讲解，见 `AGENTS.md`。
